# SEAM V2 rebuild plan

## Core decisions

SEAM should be positioned as **portfolio-first, with internal-tool UX, and explicitly non-commercial**. That framing matches the rebuild PRD, which already treats recruiters and interviewers as a core audience, and it also matches the current source stack in the existing urlSEAM repohttps://github.com/shawnkhattak/SEAM, which mixes commercial and non-commercially licensed data sources. In other words, the project should optimize for clarity, explainability, setup speed, demo quality, and interview value rather than monetization, account systems, or multi-tenant hardening. fileciteturn0file0 citeturn3view2turn8search16

V1 should ship with **no user auth at all**. Not multi-user auth, and not even a real admin system. The rebuild PRD already makes “no user login/authentication in Version 1” a non-goal, while the current repo exposes a default admin token and runtime config flows that are unnecessary for a resume project. The better compromise is structural, not auth-based: keep all write actions under a `/api/dev/*` namespace, make them visible only in local/dev mode, and add a build flag that can disable mutation routes when you want to show a read-only public demo later. fileciteturn0file0 citeturn0view0turn3view2

Treat the project as a backend-owned client for urlOCEANS-Xturn8search1. Under your stated assumption, access is guaranteed and there is no practical quota, but the surfaced public docs emphasize API-key authentication and I did not find a surfaced public rate-limit statement in the docs I checked, which makes conservative request budgeting the safer engineering choice anyway. The rebuilt system should therefore stay manual-first in development, perform on-demand enrichment only when a user explicitly asks for it, dedupe writes aggressively, and never let the frontend call OCEANS-X directly. That also matches the rebuild documents, which already recommend manual ingestion during development to reduce accidental overuse and simplify debugging. fileciteturn0file0 fileciteturn0file1 citeturn11search0turn13search0turn13search1

For storage, choose entity["software","PostgreSQL","relational database"] plus entity["software","PostGIS","spatial extension for PostgreSQL"] for V1 and **drop** entity["software","TimescaleDB","time-series extension for PostgreSQL"] from the rebuild. The reason is simple: the rebuild PRD explicitly excludes historical snapshots in V1, and the technical plan already treats V1 as latest-position oriented; meanwhile, the current repo adds a Timescale-specific Docker image and Timescale hypertables for position tables. The official PostgreSQL docs say declarative partitioning is suitable for most common use cases, while official Timescale docs add extension-install and version-compatibility requirements that are avoidable overhead in a portfolio-first MVP. My recommendation is slightly stricter than the two options you offered: use plain PostgreSQL now, and do **no partitioning at launch** unless you actually introduce a history table; if history arrives in V1.1 or V2, start with native monthly range partitions before reconsidering Timescale. fileciteturn0file0 fileciteturn0file1 citeturn2view1turn4view0turn6view0turn7search1turn7search7

AI should remain **disabled in V1**. Do not expose explanation buttons, do not wire provider SDKs into the first stable release, and do not let a coding agent sneak AI back in “for now.” What should be built instead is the evidence layer AI would require later: raw payload retention, source timestamps, reversible matching logic, edge evidence summaries, and transparent risk flags. That is cleaner than the current repo and stricter than the earlier technical plan, and it aligns directly with the PRD rule that AI may only explain stored facts and may not guess. fileciteturn0file0 fileciteturn0file1

## Audit of the current SEAM build

The current build in the urlSEAM repohttps://github.com/shawnkhattak/SEAM already contains several ideas worth preserving in spirit: one-command local startup, a serious maritime scope, field-level provenance, a vessel-to-company relationship model, and an offline/mock mode for local development. Those are genuinely valuable because they make the project runnable, explainable, and demoable without requiring immediate external connectivity. citeturn0view0turn3view2turn4view0

Where the current version goes wrong is **breadth before stability**. The README promises a map-first dashboard with shadow-fleet detection, sanctions exposure, risk scores, news, weather, admin configuration, mock/live switching, and scheduled ingestion; the backend dependencies include scheduling and AI-related packages; the database path includes Timescale; and the frontend is presently built around entity["software","Leaflet","JavaScript mapping library"] while the rebuild plan already recommends entity["software","MapLibre GL JS","WebGL web mapping library"]. That is a lot of moving parts for a project whose own rebuild documents define V1 as backend-first, manual-ingestion, no-auth, no-numeric-risk-score, and no unsupported AI. citeturn0view0turn3view0turn3view1turn6view3 fileciteturn0file0 fileciteturn0file1

The rebuild should therefore be a **reset, not a refactor marathon**. Tag the current version as legacy, preserve any parsing logic or captured payloads that are truly reusable, and rebuild the runtime from a clean monorepo with narrower boundaries. In practical terms, V2 is not “V1 plus more.” It is “V1 minus unnecessary surface area, plus better evidence and better stability.” fileciteturn0file1 citeturn0view0turn3view2

## Recommended target architecture

The backend should stay on entity["software","FastAPI","Python web framework"] with entity["software","SQLAlchemy","Python ORM"] and entity["software","Alembic","database migration tool"], because that was already the strongest part of the uploaded technical direction and it is a good fit for a portfolio system that needs strong APIs, explicit models, and clean migrations. The internal modules should be simpler than the current repo: `core`, `db`, `models`, `schemas`, `api/routes`, and `services` with subpackages for `oceans_x`, `ingestion`, `matching`, `graph`, `risk`, and `meta`. Keep the adapter boundary strict: only the Oceans-X client talks to OCEANS-X; only ingestion services write source payloads; and only API routes shape public responses. fileciteturn0file1 citeturn6view4

The database should be evidence-first but lighter than the current repo’s SCD2-heavy approach. Keep normalized core tables for `vessels`, `vessel_positions_latest`, `port_events`, `entities`, `relationships`, `risk_flags`, `sanctions_records`, `news_articles`, `reference_data`, `ingestion_jobs`, `ingestion_logs`, and `source_health`. Add a single provenance backbone such as `evidence_items` or `source_observations` so that every relationship and risk flag can point back to a source record, fetch time, and payload hash. That preserves the current repo’s strongest idea—traceable facts—without dragging full field-history complexity into V1. Also keep the PRD’s rule of transparent risk flags and explicitly reject numeric risk scoring in V1. fileciteturn0file0 fileciteturn0file1 citeturn3view2turn4view0

The frontend should use entity["software","React","JavaScript UI library"] with entity["software","Vite","frontend build tool"] and TypeScript, following the uploaded technical plan. Switch the map stack from the current entity["software","Leaflet","JavaScript mapping library"] setup to entity["software","MapLibre GL JS","WebGL web mapping library"]. That change is worth making because MapLibre’s official docs describe a WebGL renderer with vector-tile support, and its large-data guidance explicitly recommends performance tactics such as simpler styles and lower `maxZoom` for large point sources. Since a vessel map is a central portfolio surface for SEAM, this is a meaningful architectural improvement rather than cosmetic churn. fileciteturn0file1 citeturn3view0turn6view2turn6view3

The graph layer should be split into **two different experiences**. For entity and vessel relationships, use entity["software","React Flow","React node-based UI library"] because evidence panels, filters, and inspectable edges matter more than animation. For portfolio storytelling, add a separate custom canvas-based schema visualizer later. This separation is one of the best improvements you can make to the idea: the analyst graph answers operational questions, while the portfolio graph explains the system itself. fileciteturn0file0 fileciteturn0file1 fileciteturn0file3

Operationally, V1 should be almost boring: three runtime services only—frontend, backend, and PostgreSQL/PostGIS—plus `.env.example`, `start.sh`, and `stop.sh`. No scheduler, no worker, no Redis, no runtime secret editor, and no admin auth. One thing worth keeping from the old build is the idea of a no-key demo path, but it should become a **recorded-real-data replay mode**, not fake vessels. Capture small real payload fixtures from OCEANS-X and replay them locally for tests, screenshots, and recruiter demos. That preserves the PRD’s “no fake/demo data” rule while keeping the project easy to run. fileciteturn0file0 fileciteturn0file1 citeturn3view2

## Chronological implementation plan

The sequence below intentionally follows the spirit of the uploaded PRD and technical plan, but tightens the scope around stability, evidence, and portfolio value. Each stage should be completed before the next one starts.

1. **Archive the current version and freeze scope.** Create a `legacy-v1` tag, move any old design notes into `docs/archive/`, capture the current screenshots and demo GIFs while the old app still runs, and write a one-page V2 charter that explicitly says: no auth, no AI, no Timescale, no numeric risk score, no scheduler. Done when the old version is safely preserved and the rebuild has a one-page contract that future coding sessions cannot drift away from. citeturn0view0turn3view2 fileciteturn0file0

2. **Create the clean monorepo shell.** Build a fresh root with `backend/`, `frontend/`, `docs/`, `.env.example`, `docker-compose.yml`, `start.sh`, and `stop.sh`. The shell should boot three services only, return `/api/health`, render a blank frontend shell, and include a `docs/adr/` folder for architecture decisions from day one. Done when a fresh clone can start cleanly and show a backend health response plus a visible frontend frame. fileciteturn0file1

3. **Define the V1 schema and migrations before any real API work.** Create tables for vessels, latest positions, port events, entities, relationships, risk flags, sanctions, news, ingestion jobs/logs, source health, reference data, and evidence/provenance. Do **not** create a historical position archive yet, and do **not** introduce Timescale-specific constructs. Done when migrations run cleanly, database indexes exist, and the backend can round-trip basic CRUD for every core table. fileciteturn0file0 fileciteturn0file1 citeturn2view1turn4view0turn6view0

4. **Build the ingestion framework before connecting OCEANS-X.** Implement the `OceansXClient`, request timeout/retry logic, structured ingestion jobs, ingestion logs, and source-health updates. ## Roadmap page and fluid web plan

Build `/roadmap` as a **content-driven portfolio page**, not as a database feature. The interaction language in your reference file is strong: a cinematic hero, phase filters, animated milestone cards, progress bars, and a polished “what exists / what is next” story. Recreate that feel in app-native React components, but load the content from `docs/roadmap/*.md` or `frontend/src/content/roadmap.ts` instead of hardcoding it into one giant HTML file. That way the page becomes maintainable, can be updated after each milestone, and can link directly to ADRs, screenshots, demo clips, and completed issues. fileciteturn0file2 fileciteturn0file1

Build the fluid database visualization as `/schema` or `/datagraph`, and treat it as an **interactive architecture atlas**. Your reference file already points toward the right interactions: drag, zoom, search, domain filters, focus, counts, and a detail panel. The improvement is that the page should be generated from first-party schema metadata rather than staying a static artwork. In practice, the backend should expose a metadata endpoint such as `GET /api/meta/schema-graph`, returning nodes for tables/domains and edges for foreign-key or conceptual links, while the frontend renders a custom canvas force layout with stable domain clusters for vessel, position, organization, risk, news, geo, admin, and docs. fileciteturn0file3 citeturn4view0turn3view2

Do **not** use the fluid web as the main analyst graph. That is the most important design distinction here. The main graph page should remain an evidence explorer for vessels, companies, sanctions, port events, and news. The fluid web should explain the architecture of SEAM itself. Keeping those two visualizations separate is what makes both of them better. fileciteturn0file0 fileciteturn0file1 fileciteturn0file3

## Release standard and coding-agent guardrails

SEAM V1 is done when three things are simultaneously true: the local setup is one-command and reliable; the backend can ingest and explain real entity["country","Singapore","sovereign city-state"] maritime activity without unsupported guesses; and the frontend tells a coherent story through `/dev`, the map, detail pages, the relationship graph, the roadmap page, and the schema page. That is the definition that matters for a portfolio-first project, and it is consistent with the rebuild PRD’s MVP goals and the technical plan’s definition of done. fileciteturn0file0 fileciteturn0file1

The coding-agent guardrails should be strict. Finish one stage completely before the next begins. Never add a page before its data contract exists. Never add an ingestion job without logs and source health. Never reintroduce auth, AI, numeric risk scoring, or Timescale into V1. Prefer deleting unstable old code over “temporarily” adapting it. If a stage threatens the timeline, cut feature breadth before you cut evidence quality or boot reliability.
